# Граница Фазы I: API, подпись, документация, данные и исходный код

> **Статус:** внутренняя граница подтверждена; source code остаётся отдельным договорным выбором клиента, API/документация и юридическая модель подписи вынесены на подтверждение C-27–C-30.

## 1. API и интеграционная готовность

### Что прямо требуется

Общая архитектура должна иметь полный API-слой и позволять добавлять внешние системы без переработки core. Поставщик должен передать техническое описание API и правила его использования; ограничения API раскрываются до договора.

Основание: §§9.2 и 10.4, строки 7186–7204 и 7378–7386.

### Что не требуется автоматически в I

Конкретные государственные, страховые, бухгалтерские, платёжные, лабораторные, PACS, медицинские device и другие внешние коннекторы описаны в модуле интеграций будущей фазы. В I глубокие внешние интеграции прямо исключены.

Основание: §6.8.8, строки 3637–3661; §8.6, строки 5932–6333.

### Реальная неоднозначность

API является общесистемным обязательным принципом, но:

- закрытый список внешних endpoints для I отсутствует;
- форматы, authentication, versioning и rate limits не определены;
- документированный API отдельно фигурирует в приёмке будущего integration-модуля;
- не сказано, должен ли клиент получить документацию внутренних API приложения или только стабильный внешний integration API.

### Предлагаемая минимальная граница

> В I входит API-архитектура и документированный базовый integration interface с согласованными правилами authentication, versioning и ошибок. Конкретные внешние коннекторы и дополнительные business endpoints входят только по закрытому перечню договора и иначе оцениваются отдельно.

## 2. Электронное подтверждение и внешняя подпись

### Внутреннее подтверждение I

I требует различать автора, редактора и утверждающего; финальное подтверждение хранит пользователя, дату и время и действует согласно роли и типу документа.

Основание: §6.7.4.Ը, строки 3167–3191.

### Внешняя квалифицированная электронная подпись

Интеграция со средствами электронной подписи описана внутри внешнего integration-модуля будущей фазы. Она должна позволять подписывать юридически значимые документы и хранить verification data.

Основание: §8.6.12, строки 6197–6221.

### Предлагаемая граница

> В I входит только внутреннее системное подтверждение с пользователем, ролью, датой, временем, версией документа и Audit Trail. Интеграция с квалифицированной электронной подписью, сертификатами и внешним trust service не входит и оценивается отдельно.

Для заявленной работы без параллельной бумаги клиент должен юридически подтвердить, для каких документов внутреннего подтверждения достаточно, а какие необходимо печатать/подписывать вручную до будущей e-sign интеграции.

## 3. Данные и полный экспорт

Все медицинские, финансовые, справочные, аналитические данные, документы, настройки и цифровые материалы являются собственностью клиента. Клиент должен в любое время получать структурированный читаемый экспорт данных, включая пользователей и Audit Trail, без дополнительной лицензии или отдельного разрешения поставщика.

Основание: §§9.8 и 10.2–10.3, строки 7306–7376.

Это обязательство относится к данным, но не означает автоматическую передачу программного кода.

Открыты формат полного экспорта, сроки его подготовки, способ передачи крупных файлов и допустимо ли взимать оплату за разовую техническую работу при сохранении бесплатного права на экспорт.

## 4. Обязательная техническая документация

Источник требует передать в электронном виде и обновлять:

- описание архитектуры;
- описание структуры базы данных;
- описание интеграций;
- описание API;
- deployment guide;
- operations guide;
- maintenance guide;
- backup/restore procedure;
- update procedure;
- user manuals.

Основание: §10.5, строки 7386–7410.

Перечень обязателен, но уровень детализации, формат, язык, версия `as-built`, период обновления и включение схем, OpenAPI, runbooks и deployment scripts не определены.

## 5. Исходный код и независимость клиента

### Что написано

Передача source code не обязательна и должна регулироваться отдельным договорным условием. Если код не передаётся, клиент всё равно не должен терять права использовать и экспортировать данные, создавать интеграции, расширять систему и привлекать другого поставщика.

Основание: §§10.9–10.10, строки 7464–7500.

### Проблема

Без исходного кода другой поставщик сможет создавать внешние интеграции через API, но не обязательно сможет исправлять или изменять core. Поэтому договор должен честно выбрать одну модель:

1. передача repository/source code и необходимых прав;
2. лицензия на использование без передачи core-кода, с расширением только через API;
3. escrow или условная передача кода при прекращении поддержки.

Источник не выбирает модель и не определяет права на сторонние/open-source компоненты, repository, CI/CD и deployment scripts.

## 6. Внутренние ответы

### X-01. Исходный код

**Ответ источника:** автоматическая передача source code не требуется. §10.10 прямо говорит, что она выполняется только тогда, когда предусмотрена договором, и её условия должны быть установлены отдельно.

**Внутренняя позиция:** исполнитель готов передать исходный код, если это понадобится клиенту и будет прямо включено в договор. Необходимо отдельно определить repository, состав кода, историю, deployment/build materials, момент передачи, права изменения, возможность привлечения другого разработчика и исключения для third-party компонентов.

### X-02. API-deliverable I

**Подтверждено:** поскольку это прямо требуется §§9.2 и 10.4, в I входят API-фундамент и документация согласованного integration interface. Конкретные внешние коннекторы и дополнительные business endpoints оплачиваются отдельно.

### X-03. Документация

**Ответ источника:** весь перечень §10.5 обязателен. §10.11 также требует передать всю техническую документацию до финальной приёмки.

**Внутренняя позиция:** в цену входит электронный комплект `as-built` на момент финального акта: architecture, DB structure, integrations/API, deployment, operations, maintenance, backup/restore, update procedure и user manuals. Неограниченное обновление документации после акта входит только в maintenance или новую разработку.

### X-04. Полный экспорт данных

**Подтверждено:** клиент имеет право на полный структурированный экспорт всех своих данных без отдельной лицензии или разрешения. Стандартный согласованный export mechanism входит. Нестандартное преобразование, специальный формат или разовая ручная подготовка большого package могут оцениваться отдельно без ограничения самого права клиента на данные.

### X-05. Электронная подпись

**Подтверждено:** исходник требует для I внутреннее подтверждение и Audit Trail. Внешняя квалифицированная e-sign интеграция находится в будущем integration-модуле и не входит. Юридическую достаточность внутреннего подтверждения для безбумажного запуска подтверждает клиент.

### X-06. Права на сторонние компоненты

**Подтверждено:** клиенту передаётся перечень сторонних/open-source компонентов и применяемых лицензий. Коммерческие лицензии, подписки и recurring third-party costs раскрываются и оплачиваются отдельно, если прямо не включены в коммерческое приложение.
